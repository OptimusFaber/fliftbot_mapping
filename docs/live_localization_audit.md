# Сверка live-локализации с lidar_localization.txt — 06.11.2026

Итоговая команда в истории от 08.10: DePHAN, yaw=180°, legacy sin,
wheelbase=1,41 м, sampling сканов=0,5, global sampling=0,5, оптимизация через
10 nodes, correlative окна 0,15 м / 10°, выходная поправка (−0,04; −0,045) м,
ContinuousNav 10 Гц. В истории использовались другие измерения и частота
лидара 25 Гц. Текущая рекомендация пользователя — 20 Гц после аппаратных сбоев.

## Код и совместимость

- `odom_model=legacy_sin` сохраняет формулу `vx=v`, `wz=v*sin(delta)/L`.
  `use_legacy_sin` — только alias для старых команд: true=legacy_sin,
  false=bicycle. Его отдельная реализация не нужна. Противоречивое сочетание
  alias и `odom_model` отклоняется.
- В старом bundled-профиле DePHAN yaw≈176,73°, а общий live default global
  sampling=0,2 и pose offsets=(0;0). Поэтому команда из README задаёт выбранные
  исторические значения явно. Defaults новой карты читаются из её bundle;
  им не подменяется калибровка старого эксперимента.
- Исправлен отсутствующий импорт `LIDAR_VARIANCE`: ранее live exporter падал
  при включённой передаче ContinuousNav ещё на стартовом сообщении журнала.
- Проверена настоящая локальная ZMQ-передача с включённым exporter:
  поворот offsets в систему корпуса, перевод градусов в радианы,
  variance и запрет повторной отправки одного timestamp.
- Уменьшена частота предупреждений `send would block`: не чаще одного
  сообщения за 5 секунд.
- Исправлена передача `configuration_basename` в initializer: ранее сервис
  `/start_trajectory` всегда получал стандартное имя независимо от launch.
- Добавлены доступные через launch настройки UDP-порта/source IP, scan_time,
  дальности скана и steering sign. `scan_rate_hz` меняет только метаданные
  LaserScan; реальный датчик не перенастраивает.
- README содержит Docker/ROS-подготовку, полный исторический запуск,
  запуск новой карты, проверку частот/TF, единицы углов, выходные журналы,
  все параметры live-launch и фиксированные значимые параметры Lua.

## Проверка на записанных данных

Источник: `ros-data/recordings/real/20261002/155456_dephan_m360_room`, первые
90 секунд. Независимый от построения карты проезд того же помещения.
Карта: bundled `dephan_20260922_corrected_run_170557/map.pbstream` от 22.09.
Поданы 2237 сканов и выбранные encoder samples. Все варианты используют
одну начальную позу, полученную scan-only occupancy/ICP, один map reference,
одни и те же настройки Cartographer и калибровку старого live-профиля.
Проверка выполняется реальным ROS Cartographer с frozen map, преобразованием
скана через используемый live `points_to_scan`, общей моделью одометрии и
настоящим `live_marker98_pose.py`. Передача физическому контроллеру отключена.

Параметры моделей меняются только через `model`; общий steering zero −90°,
speed sign −1, wheelbase 1,41 м. Это сравнение моделей на старой калибровке,
а не независимый подбор правильного steering zero для каждой модели.

Воспроизведение ускорено вдвое; время сканов/энкодеров сохраняется в общей
перебазированной шкале `/clock`. Сравнивается весь live TF-журнал, а не только
выжившие nodes графа: pure-localization trimmer удаляет старые узлы.
Эталон для сравнения — `nav_x/nav_y/nav_dgr/nav_t` из move logger,
с фиксированным reference карты и без подбора пространственного/временного
смещения отдельно для каждой модели. Это расхождение с навигационным логом,
а не гарантия абсолютной GT-точности потолочной системы.

Записанный CSV получен через `mc_dict_from_msg`: скорость там уже равна
`-MC.enc_lin_vel_mps`. Поэтому для воспроизведения **сырого MC-контракта**
используется `--encoder-speed-scale=-1`, после чего применяется тот же
`speed_sign=-1`, что в live. Промежуточные прогоны с ошибочным знаком помечены
`INVALID_REPLAY.txt` и не используются для выводов.

Численные результаты и журнал сохранены в:

```text
ros-data/results/live_localization_audit_20261106_mc_contract/
  manifest.json
  reference.csv
  reference_comparison.json
  legacy_sin/live_pose.csv.journal.jsonl
  legacy_sin/live_report.json
  drive_wheel/live_pose.csv.journal.jsonl
  drive_wheel/live_report.json
  bicycle/live_pose.csv.journal.jsonl
  bicycle/live_report.json
```

Срывы в этой проверке — непрерывное отсутствие свежей позы либо ошибка
свыше 0,20 м или 10° длительностью не меньше 0,5 с. Эти пороги взяты для
сопоставления с определением стабильности в истории. Отдельно сохраняется
доля времени с ошибкой положения не больше 5 см. Все статистики live-сравнения
взвешены по времени; пропуски эталона не подменяются нулевой ошибкой.

## Результат сравнения

На одинаковом 90-секундном участке и старой калибровке:

| Модель | Среднее расхождение положения | P95 положения | P95 угла | Эпизоды срыва |
|---|---:|---:|---:|---:|
| legacy_sin | 6,91 см | 11,43 см | 3,00° | 0 |
| drive_wheel | 96,30 см | 280,04 см | 3,05° | 2 |
| bicycle (tan) | 181,78 см | 435,88 см | 123,22° | 1 |

Доступность свежей позы около 99,77%, покрытие эталоном около 99,11% у всех
трёх вариантов. Поэтому наличие регулярной позы само по себе не доказывает
правильную локализацию: два варианта продолжали выдавать свежие ошибочные позы.
У legacy_sin всё сравнимое время проходит старые пороги 20 см / 10°,
но только около 13,0% сравнимого времени проходит порог положения 5 см.

Для воспроизведения старого варианта сохраняем `odom_model=legacy_sin`.
Отдельный `use_legacy_sin` для вычислений не требуется; он оставлен только
для старых команд. Эти результаты не доказывают, что `drive_wheel` хуже
при любой калибровке: здесь все три варианта намеренно использовали старый
steering zero −90° и ту же карту. Новые карты со своей калибровкой и моделью
должны проверяться отдельно. Показатели из исходных logs5 (5,1 см в среднем)
не воспроизведены на другом проезде автоматически.

## Воспроизведение проверки

Из workspace, после загрузки ROS Humble:

```bash
source /opt/ros/humble/setup.bash
ROS_DOMAIN_ID=171 ROS_LOCALHOST_ONLY=1 \
  fliftbot_lidar_nav/.venv/bin/python tools/verify_live_localization_recording.py \
  --recording ros-data/recordings/real/20261002/155456_dephan_m360_room \
  --duration 90 --rate 2 --encoder-speed-scale=-1 \
  --output /data/new_live_localization_audit

fliftbot_lidar_nav/.venv/bin/python tools/compare_localization_audit.py \
  --audit /data/new_live_localization_audit

ROS_DOMAIN_ID=172 ROS_LOCALHOST_ONLY=1 \
  fliftbot_lidar_nav/.venv/bin/python fliftbot_lidar_nav/scripts/verify.py
```

Каталог результата replay должен быть новым. Значение speed scale относится
к выбранной CSV-записи; для другой записи сначала проверьте её контракт.
Инструмент не читает эталон для локализации и не подстраивает по нему seed.

27 автоматических тестов прошли, включая сборку launch-команд без запуска
робота, совместимость sin/tan alias, модель скорости и знак CSV/MC,
полноту таблицы параметров README, live exporter и ZMQ, сценарные отчёты.
`ros2 launch … --show-args`, Python syntax и `git diff --check` также прошли.

Проверка не является запуском на физическом роботе и не повторяет logs5:
исходных файлов `navigation_logs/logs5` на этой машине не обнаружено.
Приём реальных UDP-пакетов, фактический MC-поток и конкретный работающий
ContinuousNav в контейнере робота требуют проверки на самом роботе.
