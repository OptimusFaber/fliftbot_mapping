# Журнал и оценка испытаний

Live Cartographer сохраняет прежний pose CSV и отдельный JSONL-журнал
`CSV.journal.jsonl`. Файл журнала создаётся исключительно заново: задавайте
новый путь для каждого заезда. ROS не требуется для анализа журнала.

```bash
./fliftbot_lidar_nav/nav.sh live --sensor dephan --map-dir /data/deploy/run01 \
  scenario_config:=/data/scenarios/route01.json \
  marker_pose_csv:=/data/trials/run01/poses.csv

./fliftbot_lidar_nav/nav.sh sim --map-dir /data/deploy/run01 \
  scenario_config:=/data/scenarios/route01.json \
  journal:=/data/trials/sim01/journal.jsonl

./fliftbot_lidar_nav/nav.sh localize-recording \
  --recording /data/canonical/run01 --map-dir /data/deploy/run01 \
  --scenario-config /data/scenarios/route01.json --output /data/trials/replay01

./fliftbot_lidar_nav/nav.sh report \
  --journal /data/trials/run01/poses.csv.journal.jsonl \
  --reference /data/trials/run01/ceiling_reference.csv \
  --output /data/reports/run01
```

Шаблон: `config/scenarios/example.json`. Порог положения — 0,05 м.
Ориентационный порог оставлен `null`: его нужно согласовать и задать в градусах.
Остальные значения шаблона являются начальными настройками методики,
а не согласованными критериями испытаний. Приложение сохраняет фактические
настройки в начале каждого журнала.

`route_start_s` и `route_end_s` задают границы оцениваемого маршрута в шкале
времени журнала. Без них оценивается интервал от первой записи состояния до
штатной остановки. Для согласованного маршрута укажите обе границы: ожидание
до старта и время после финиша не должны влиять на результат. Незарегистрированные
части объявленного маршрута считаются недоступными. Незавершённый журнал
анализируется, но успешным не объявляется.

## Что записывается

- `run_start`: ID заезда, сценарий, параметры и сведения об алгоритме/геометрии;
- `sample`: время проверки и исходного измерения, поза в метрах/радианах,
  возраст, свежесть, признак нового измерения, состояние;
- `event`: смена доступности позы, восстановление/пропадание входного потока,
  подозрительный скачок позы;
- `run_end`: штатная остановка.

Live-журнал также содержит число допустимых лучей последнего скана, интервалы
его получения, времена сканов/одометрии, скорость по одометрии. Наличие
потока определяется по времени получения; исходные timestamps сохраняются
для диагностики задержек. Скачок определяется по настраиваемому приращению
положения/угла между новыми оценками, сохраняется с интервалом времени и
служит диагностикой: его нельзя автоматически считать доказанным срывом.
Повторная поза считается доступной только до истечения `max_pose_age_s`.

Журнал не меняет выходную позу или алгоритм Cartographer. RMSE и overlap
записываются в offline ICP replay, где они действительно рассчитываются.
Live Cartographer таких значений через TF не предоставляет. Offline ICP
и live Cartographer — разные алгоритмы; их журналы помечены соответственно.
Сброс ROS-времени требует отдельного заезда: отчёт отклоняет обратный ход часов.

## Эталон и сравнение

CSV имеет обязательный заголовок `ts,x,y,yaw_rad`. Положение задано относительно
той же точки робота и в той же системе координат, что и журнал; время — в
той же шкале. Live pose CSV содержит `alpha_deg`: перед сравнением переведите
углы в радианы. Оценки, полученные с участием этого же LiDAR в объединённой
навигации, не являются независимым эталоном потолочной системы.

`--reference-time-offset-s` добавляется к времени эталона. Настройки времени
и координат определяются независимо и фиксируются до сравнения; автоматической
подгонки по оцениваемому маршруту нет. Интерполяция угла учитывает ±π;
интерполяция через разрыв длиннее `max_reference_gap_s` запрещена.

Результаты — `report.json`, краткий `report.md`, `errors.csv` и `events.jsonl`:

- горизонтальная ошибка положения, абсолютная ошибка угла: медиана, P95,
  максимум и RMSE, взвешенные по времени;
- разброс знаковой ошибки ориентации относительно её среднего по окружности;
  он отделяет колебания ошибки от постоянного смещения угла;
- доступность свежей позы и покрытие маршрута эталоном;
- доля сравнимого времени в пределах каждого порога;
- число/длительность эпизодов недоступности и объединённых срывов
  (недоступность либо превышение одного из заданных порогов);
- события превышения порога с ID сценария, интервалом, максимальной
  наблюдённой ошибкой и принятым порогом. Все сравнимые значения есть в CSV.

Эпизод учитывается, если длится не меньше `min_event_duration_s`. Соседние
ошибочные отсчёты объединяются; краткие восстановления разделяют эпизоды.
Неизвестная ошибка во время отсутствия эталона не подменяется нулём.
Доступность оценивает наличие свежей позы, её точность проверяется отдельно.

## Классификация

`successful_single_run` означает: журнал завершён, эталон покрывает достаточную
часть маршрута, задан порог угла, доступность и доли времени в пределах порогов
проходят критерии сценария, число срывов не превышает допустимое.
`partially_successful` означает, что критерии выполнены на части маршрута либо
для одной компоненты. `unsuccessful` — свежих оценок нет либо ни одна компонента
не проходит пороги на сравнимых участках. `insufficient_evidence` — для заключения
не хватает покрытия эталоном или порога ориентации.

Это оценка одного проезда. Повторяемость траектории и окончательный успех
сценария требуют повторных проездов согласованного маршрута и сопоставления
одинаковых участков; текущий отчёт явно помечает их как не оценённые.
Расхождение с потолочной системой характеризует сравнение систем. Заявление
об абсолютной точности до 5 см требует учёта точности выбранного эталона.
Качество геометрии построенной карты отдельно этими метриками не измеряется.
